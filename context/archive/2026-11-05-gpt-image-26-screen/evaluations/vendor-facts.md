## Notes

1. **Custom sizes are not confirmed for 2.6 by name.** The series requests 2336×1552, 2192×1648 and 2320×1552 — all
   multiples of 16, aspect ≤ 3:1, inside the pixel range and under the 2560×1440 pixel count. The guide grants custom
   `WIDTHxHEIGHT` to the Sunburst and Flare families; the edit reference's explicit list omits the 2.6 ids. If 2.6
   rejects these sizes, the call returns a non-transient HTTP 400 that is neither retried nor charged as an output, and
   the slot is undelivered — the screen would then FAIL as "not delivered", never as a fidelity loss. The plan keeps the
   phase-5 size rule unchanged, so this is recorded as a risk, not changed here.
2. **The Batch listing does not affect the screen.** The runner calls the synchronous edits endpoint at standard rates;
   the cost bound uses the standard rates.
3. **Rates re-checked against the cost bound.** The config keeps the phase-5 bound: $30/M output image, $8/M input
   image (both equal to the live rates) and $10/M for text (above the live $5/M). The bound's token densities come from
   GPT Image 2.5's measured usage; 2.6's usage is unknown, so a response above the bound still stops the runner.
4. **Premise holds.** `complexity=low` and `moderation=auto` are both accepted by `v1/images/edits`, so the plan's stop
   condition ("If `complexity=low` or `moderation=auto` is not accepted by the edits endpoint, stop") did not trigger.
5. A guide sentence and the edit reference disagree on whether 2.6 supports `xhigh`/`max` quality. The screen uses
   `high`, which both pages allow.
