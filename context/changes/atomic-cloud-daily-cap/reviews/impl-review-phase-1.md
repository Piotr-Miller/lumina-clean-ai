## Findings

### F1 — `SECURITY DEFINER` unnecessarily widens the privilege boundary

- **Severity**: ⚠️ WARNING
- **Impact**: 🔎 MEDIUM — real tradeoff; pause to reason through it
- **Dimension**: Safety & Quality
- **Location**: `supabase/migrations/20260828120000_atomic_cloud_daily_cap.sql:55`
- **Detail**: The RPC is executable only by `service_role`, which already has `BYPASSRLS` and explicit `SELECT`/`INSERT` grants on `public.jobs`. It therefore does not need owner privileges. The current ACL is secure, but `SECURITY DEFINER` turns any future execute-grant regression into a postgres-privileged insertion endpoint accepting caller-controlled job, user, path, and cap values.
- **Fix**: Change the function to `SECURITY INVOKER` or omit the clause; retain the empty search path and service-role-only execute ACL. Update the plan, comments, and Phase 4 verification to expect `prosecdef = false`.
  - Strength: Preserves atomicity while limiting the consequences of future ACL mistakes.
  - Tradeoff: Requires updating the reviewed contract and rerunning the migration/integration verification.
  - Confidence: HIGH — the local catalog confirms `service_role` has `BYPASSRLS` plus the required table privileges.
  - Blind spot: The invoker variant has not yet been exercised through PostgREST in this branch.
- **Decision**: ACCEPTED (2026-08-28) — function switched to `security invoker`.
  - Premise verified on the local stack: `service_role` is `rolbypassrls = t` and holds `INSERT,SELECT` on `public.jobs`, so owner privileges add no capability.
  - Consequence measured, not assumed: with `execute` leaked to `authenticated`, the INVOKER form fails `permission denied for table jobs` and inserts **0** rows; the DEFINER form returns `true` and inserts **1**, with a caller-controlled `p_user_id` and `p_source_path` — defeating the authenticated-INSERT revoke in `20260621185226`.
  - Blind spot closed: all 29 tests in `tests/jobs.rls.test.ts` pass under the invoker variant, exercised through PostgREST. Atomicity is unaffected (the advisory lock is privilege-independent).
  - Nine plan passages updated, including Phase 4's expectation → `prosecdef = false`. Root cause recorded in the migration header and `plan.md` § Review Response — Phase 1: the reaper precedent needs DEFINER because it reads `storage.objects`; this function does not.

### F3 — Exact repository-wide formatting gate is not currently reproducible

- **Severity**: OBSERVATION
- **Impact**: 🏃 LOW — quick decision; fix is obvious and narrowly scoped
- **Dimension**: Success Criteria
- **Location**: `supabase/.temp/start-secrets/supabase_edge_runtime_10x-astro-starter/main/index.ts`
- **Detail**: `npm run format:check` fails on a gitignored runtime file generated by the local Supabase reset. The tracked Phase 1 JavaScript/TypeScript files pass targeted Prettier checking, and `git diff --check` passes. Because the plan requires the exact repository-wide command, its criterion is not currently green on this checkout.
- **Fix**: After local-stack verification, clear only the generated Supabase temporary artifact and rerun the exact formatting command.
- **Decision**: ACKNOWLEDGED, deferred as out of scope (2026-08-28). Reproduced and diagnosed, with two corrections to the finding's framing:
  - **Not caused by this change, and not new.** `supabase/.temp/**` is gitignored via the _nested_ `supabase/.gitignore`, which Prettier never reads — the identical blind spot `eslint.config.js` already documents and works around with `{ ignores: ["supabase/.temp/**"] }`. It fails on any branch, including `master`, whenever the local stack is running, and is green whenever it is down. Phase 1's original green result was legitimate: the stack was not yet started.
  - **CI is unaffected.** The `ci` job runs `npm run format:check` and never starts Supabase — that is the separate `integration` job — so `supabase/.temp/` never exists in that checkout. The plan's criterion is green where it is gated.
  - Deleting `.temp` satisfies the literal command once but regenerates on every `supabase start`, so it would recur in every remaining phase. The durable fix is a `.prettierignore` entry, but `AGENTS.md` governs that file and explicitly says not to add subtrees to silence drift — so it needs its own change and its own justification, not a quiet Phase 1 edit.
