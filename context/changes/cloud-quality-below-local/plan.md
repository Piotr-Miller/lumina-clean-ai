# Calibrate Cloud Auto exposure and verify quality against Local — Implementation Plan

## Overview

Calibrate the Cloud AI (Bread) branch of the Auto recommendation so it stops overexposing night
photos, then decide S-17 on the frozen benchmark `s17-v1` against the agreed quality bar
(`quality-bar.md`). Two independent verdicts come out of it: whether Cloud Auto works (condition 1)
and whether Cloud is noticeably better than Local (condition 2). The product code change is small —
one branch of one pure function, plus its bounds and tests. Most of the plan is measurement: a
premise check, a pre-registered tuning procedure on six photos, a frozen regression reference, a
production deploy, and a blind validation on twelve.

## Current State Analysis

- **Cloud Auto is a pure function evaluated in the browser.** `recommendParams(stats, "cloud")`
  (`src/lib/engines/auto-params.ts:141-160`) is called from `EnhanceWorkspace.tsx:145-146, 306-307`
  on stats from `sampleImageLuma` (`auto-params.client.ts:27-43`, ≤ 512 px canvas downscale). A new
  Auto therefore ships with the app deploy, not the Edge Function. _(origin: code)_
- **Both engines share `baseGamma`** (`auto-params.ts:107-114`): `log(p50)/log(target)` with target
  0.3 (0.26 when `shadowRatio > 0.65 && p95 < 0.65`), ×0.8 when `p95 > 0.85`, capped at 1.1 when
  `clipRatio > 0.005`. Cloud then clamps to `PARAM_RANGES.cloud.gamma` 1.0–1.5 and derives
  `strength = 0.05 + 0.15·clamp((0.3 − p50)/0.3)` ×0.7 on `p95 > 0.85`, ≤ 0.1 on clipping
  (`:151-159`). A dark frame with no clipped lights reaches the 1.5 clamp when `p50 ≲ 0.164`.
  _(origin: code)_
- **The confirmed defect**, from `defaults-experiment.md` § Direct runs: on one licensed aurora at
  896 px, Auto's 1.50 / 0.1216 put 77.6 % of pixels at V ≥ 0.90 and 49.7 % with a clipped channel,
  against 21.3 % / 4.9 % at 1.00 / 0.05. Both parameters moved together, so it indicts the Auto
  setting as a whole. It is **one photograph at a downsampled size** — the premise is re-measured at
  full resolution in Phase 2 before anything is built.
- **Bread brightens strongly even at gamma 1.0** (Run C: mean 0.12 → 0.44). Values below 1.0 are
  blocked only by zod (`photo-job.schema.ts:31`) and `PARAM_RANGES`; the `jobs.gamma`/`strength`
  columns carry no constraint (`20260628190000_add_bread_params_to_jobs.sql`), and
  `admit_cloud_job` takes `double precision` (`20260828120000_atomic_cloud_daily_cap.sql:65-66`).
  Whether the **pinned** Bread version accepts gamma < 1.0 is unverified.
- **EXIF orientation is handled nowhere in our code.** The Cloud upload `PUT`s the original bytes
  (`cloud-upload.client.ts:87-91`); the browser applies orientation for Local and for the BEFORE
  pane. Whether Bread honours the flag is unverified. In `s17-v1` only S17-06 (validation) carries
  orientation 6.
- **The direct model path exists and is calibrated.** `scripts/spikes/bread-spike.ts` calls the same
  pinned version with the same input shape and was byte-identical to app job `04e57d16`. It sends
  local files as data URIs, which Replicate recommends only below **1 MB**; almost every `s17-v1`
  input is larger (S17-01 is 6.9 MB, S17-21 17.3 MB). Replicate's file upload accepts up to 100 MB.
- **The chroma post-pass is ON in production** — observed 2026-09-27 13:54 UTC in the served
  `luminacleanai.com` HTML (`chromaEnabled: true`; the E2E override is honoured only on loopback,
  `src/pages/index.astro:32-36`). With it ON, the Download is a post-passed JPEG, **unless** the
  processor fails, in which case the raw PNG is kept (`cloud-result-postprocess.client.ts:101-125`);
  the 12 MP guard never fires on Bread's ≤ 1536 px output. The download name follows the actual blob
  type (`useCloudJob.ts:443`). Direct runs never include the post-pass, so tuning on raw output alone
  would judge something users do not receive.
- **Existing tests** (`tests/auto-params.test.ts`) pin monotonicity, range clamps, the clip cap and
  highlight behaviour for both engines on nine fixtures under `tests/fixtures/auto-params/`,
  generated by `scripts/gen_auto_params_fixtures.py` (Pillow + numpy).
- **Daily cap**: `CLOUD_DAILY_CAP=3` in production (`production-config.md:55`), global across all
  users, resetting 00:00 UTC, enforced by `admit_cloud_job`. Twelve validation runs cannot fit one
  day at 3.

## Desired End State

- Cloud Auto no longer washes out the six tuning photos, and its S17-01 result matches an accepted
  reference within recorded tolerances — pinned by a unit test so a later formula change cannot
  silently move it.
- The candidate is live in production; Local Auto is unchanged.
- The 12 validation photos have been run through the real app on both engines, rated blind, and
  scored against both conditions. `change.md`, the roadmap, `idea-notes.md` and issue #203 state the
  verdict: condition 1 pass/fail, condition 2 pass / unconfirmed.
- The daily cap is back at 3, with both changes dated in `production-config.md`.

### Key Discoveries:

- Auto logic is client-side and pure (`auto-params.ts:141-160`) — the change is a branch edit, and
  the harness can reuse it verbatim from TypeScript instead of re-implementing the formula.
- The browser sampler downsizes to ≤ 512 px with the orientation applied (`auto-params.client.ts:13,
29-40`); an offline harness must mirror both or its Auto values drift from the app's.
- The existing fixture generator (`scripts/gen_auto_params_fixtures.py`) already sets the Pillow +
  numpy precedent for offline luma stats.
- Replicate recommends data URIs only below 1 MB; the harness needs the file-upload path.

## What We're NOT Doing

- Changing `baseGamma`, the Local branch, or Local's ranges — even if the comparison later shows a
  Local Auto problem (no speculative roadmap entry either).
- Fixing EXIF orientation inside S-17 — if needed, it is its own change (Definitions).
- Changing the chroma post-pass or its flag, the Bread version, the model, or Cloud output
  resolution/delivery (roadmap § Parked, after S-17).
- Carrying Run C/D thresholds (21.3 % / 4.9 %) or the earlier 30 % / 6 % into acceptance; exposure
  shares stay diagnostics, with no single limit across scenes.
- Committing validation outputs, or any output with a person in it. Ratings, parameters, job ids and
  sha256 are committed; images stay in `test-photos/private/`.
- Tuning on validation photos, or changing `s17-v1` membership, hashes or ROIs after experiments
  begin.
- Changing the cap's enforcement (`admit_cloud_job`) — only its configured value, temporarily.

## Implementation Approach

Measure first, build second. Phase 0 removes two already-disproven claims from the gauntlet bar. Phase 1 builds the harness that every later measurement uses: direct
Bread calls for any file size, and Auto values computed by **the app's own TypeScript** from
browser-equivalent stats. Phase 2 checks the premise at full resolution and runs the two
pre-registered probes (EXIF, gamma 0.9), with a stop gate if the premise does not hold. Phase 3
tunes on the six tuning photos only, through a fixed procedure: sweep, per-photo acceptable ranges
chosen by the maintainer, one rule over existing stats fitted inside those ranges, then the S17-01
reference accepted and frozen. Phase 4 ships that rule with tests pinning both the reference and
Local's unchanged behaviour. Phase 5 validates on the live app at a temporarily raised cap, rated
blind. Phase 6 records the verdict everywhere the old state is stated.

## Critical Implementation Details

**Pre-registration.** Every "if this fails, it means…" clause in Phases 2 and 3 is written into
`calibration.md` **before** the run it governs, and the parameter rule is frozen (commit sha
recorded) before any validation output is opened. A reading decided after the result is not a
reading.

**Sampler agreement is checked on the full `LumaStats`, not just the parameters.** Matching parameters
to two decimals can hide a sampling difference that only shows on another photo. The tuning stats
come from the app's own `sampleImageLuma` in desktop Chrome 154, using the app's Blob → `new Image()`
decode path. Compare every field on all six tuning photos with the offline harness and headless
Chromium; record differences and use the desktop values for tuning. Before model runs, verify
S17-04 in a visible desktop tab because its `clipRatio` is close to the 0.005 guard.

**Validation runs happen in the app, one photo at a time, Cloud and Local on the same file**, with
the Download used for both, and nothing tuned in between. The Cloud job id, persisted gamma and
strength, the download filename (which reveals the post-pass state) and output dimensions are
logged per photo.

## Phase 3: Tune Cloud Auto and freeze the regression reference

### Overview

Direct runs on the six tuning photos only. The maintainer chooses acceptable results, one rule over
the existing stats is fitted inside them, and the S17-01 reference is accepted and frozen.

**Entry gate** — do not start until 2.3 (premise gate: proceed), 2.4 (EXIF outcome) and 2.5 (gamma-0.9 outcome) are recorded, and 2.6 (the flag state) is written.

### Changes Required:

#### 1. Pre-registered procedure

**File**: `calibration.md`

**Intent**: Before the first sweep, record the procedure below and its stop condition: _if no single
rule over the existing `LumaStats` fields lands inside every tuning photo's acceptable range, stop
and report — do not add per-photo constants to make it fit._

**Contract**:

1. **Gamma sweep** at strength 0.05: gamma ∈ {0.9 if accepted, 1.0, 1.1, 1.2, 1.3, 1.5} on the six photos (≤ 36 runs).
2. For each photo the maintainer marks a **preferred** gamma and an **acceptable range** (no harm), from a contact sheet showing the original and each output with its diagnostics.
3. **Strength sweep** at each photo's preferred gamma: {0.05, 0.10, 0.20} plus its current Auto strength (≤ 24 runs); the maintainer marks preferred and acceptable strength.
4. **Fit** a cloud-branch mapping from existing stats to (gamma, strength): monotone in darkness, no per-photo constants, `baseGamma` untouched. It must fall inside every acceptable range and is chosen closest to the preferred values.
5. **Final-pair check** — ranges accepted separately do not guarantee a good combination. Run the fitted rule's own (gamma, strength) on each of the six photos (6 runs, no further grid) and have the maintainer rate each against its original. Any harm → the rule is not frozen; refit within the stop condition.
6. **App-path check (post-pass ON).** Before freezing, run the fitted rule on each of the six tuning photos **through the app** (its Auto must already show the fitted values — set them manually with Auto off if the candidate is not deployed yet), and rate the **downloaded** result against the original. Record per run: job id, downloaded file, format, and whether the post-pass was applied (a PNG with the flag ON means a fallback). Any harm → not frozen. Six app jobs use cap slots: at 3 a day that is about two days.
7. If the fitted rule needs gamma < 1.0, the Auto floor and slider floor are set from the chosen values, not from the probe.

#### 2. Contact sheets

**File**: `scripts/s17/` (sheet generator)

**Intent**: A local HTML sheet per photo — original plus sweep outputs at matched size, each labelled
with its parameters and diagnostics — written under `test-photos/private/`, never committed.

**Contract**: Reads harness outputs; tuning photos only (refuses a validation id).

#### 3. Regression reference

**File**: `context/changes/cloud-quality-below-local/regression-s17-01.json` (new)

**Intent**: Take S17-01's final-pair output; the maintainer visually accepts it; record the input
sha256, the exact parameters, the output sha256, the diagnostics (mean, V ≥ 0.90, any-channel-255,
hue shares), and the numeric tolerances the maintainer sets **at acceptance, for this image only**.

**Contract**: The file is the frozen reference. A later check re-runs S17-01 directly: the output
sha256 is compared first; a mismatch at identical parameters triggers an investigation of
reproducibility (recorded here), not an automatic failure; the diagnostics are then compared within
the recorded tolerances. No shared exposure limit across scenes is introduced.

### Success Criteria:

#### Automated Verification:

- The procedure and stop condition are committed before the first sweep output

## Phase 5: Validate on the twelve photos

### Overview

Run the 12 validation photos through the real app on both engines, at a temporarily raised cap, and
rate them blind against both conditions.

**Entry gate** — do not start until 4.7 and 4.8 are recorded (production shows the reference parameters; the S17-01 re-run compared with the reference) and the EXIF gate (2.4) is clear — including, if Bread ignored EXIF, the separate fix being live.

### Changes Required:

#### 1. Preconditions

**Intent**: Before the first validation run, confirm the checksums, that the Phase 4 candidate is
live, that the EXIF gate from Phase 2 is clear, and that the post-pass flag is in the same state as
during tuning. The maintainer then labels each of the 12 inputs **needs legibility improvement** or
**control**, with a one-line reason, from the inputs alone. Then write the day plan (about six
photos a day, retries included).

**Contract**: The checks, the 12 labels and the day plan are committed in `validation.md` (new, this folder) before any validation output exists.

#### 2. Cap raise and revert (maintainer)

**Intent**: The maintainer sets `CLOUD_DAILY_CAP=10` at the start of each planned day and back to `3`
at the end of **that same day, including a day that stops early**. Before each day, today's count is
checked because other users' jobs count too.

**Contract**: Every change — each raise and each revert — is dated in `production-config.md` next to
the cap's existing record and in `validation.md`. The cap is never left at 10 overnight.

#### 3. Runs

**Intent**: For each validation photo, in the app: Local on its own Auto → Download; Cloud on its own
Auto → Download. Log job id, persisted gamma/strength, the downloaded file, its format and whether
the post-pass was applied, output dimensions, and any retries. A final model-level error is logged
as a non-image result at this point, before any key exists.

**Contract**: Outputs go to `test-photos/private/s17-validation/`; only the log is committed.

#### 4. Blind sheet

**File**: `scripts/s17/` (A/B generator)

**Intent**: Build a local page per photo — original, A, B — at the Cloud result's dimensions, with
A/B assigned by a seeded random draw, and write the key to a separate file the rater does not open.

**Contract**: Local and original are downscaled with LANCZOS, and Cloud is never enlarged. The key
stores the seed and the assignment, and the page contains no engine names, filenames or dimensions
that would reveal the engine.

#### 5. Rating

**Intent**: The maintainer rates every photo. For each of A and B against the original, the rating is improvement, no harm or harm (with the bar's severe list). For A against B, the rating is which is clearly better (A / B / neither), and whether each side is not / moderately / severely worse than the other.

**Contract**: Ratings are saved to a file before the key is opened.

#### 6. Score

**Intent**: Unblind, then compute condition 1 (improvement on every needs-improvement photo, no harm on all 12, plus the regression) and condition 2 (clear Cloud wins, moderate losses, severe regressions). Apply the failure rules from the Definitions **before** tallying: an unresolved infrastructure failure means the validation is **incomplete** and no verdict is recorded; a final model-level error — the explicit exception to the both-results rule — scores as a harm and a severe regression. Record the result and the interpretation from the Definitions.

**Contract**: The scorer accepts, per photo, either two images' ratings or a recorded final model-level error (a non-image result), and refuses anything else. `validation.md` holds the per-photo table, both verdicts and the ratings file's sha256.

### Success Criteria:

#### Automated Verification:

- `sha256sum -c test-photos/s17-benchmark.sha256` passes before the first run
- The scoring script reproduces the recorded tallies from the ratings file and the key
- `npx prettier --check context/changes/cloud-quality-below-local/` passes
